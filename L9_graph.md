# L9 · Graph — the brigade

How many cooks, where the boundary between them is, and how the tray passes from one to the next. Filled from A5 and A7.

Status: decided on 2026-10-29

## A5 · Brigade? — decided on 2026-10-29

- Verdict: ☒ one cook ☐ brigade
- Stations (id · name · steps covered), 1 to 4: S1 · Research Analyst · U3, U5, U6. Candidate S2 · Thesis Critic (a new check between U5 and U9) was considered and rejected. The harness units (U1, U2, U7, U8, U9) have no model and are not a station.
- Score, 0–2 each: Size 0 (S1 covers only three units with one clear job) · Independence 0 (the critic needs the full thesis text and the same data, so it is all shared context) · Separation 1 (a second mind checking the writer has some value in principle) · Checkability 0 (the critic's objections are another plausible text the PM has to judge; they make nothing easier to verify) · Model economics 0 (both would need a strong model, so cost doubles for little gain) · Permission isolation 0 (both are read-only on the same data, nothing to keep apart) · Fault containment 1 (it might catch weak reasoning before the PM sees it). Coordination tax: −2. Total: 0.
- The boundary — why exactly there (permissions that must not mix · skills that don't coexist · failures to contain): No split. There are no permissions to separate, since everything is read-only. The failures worth containing (wrong numbers, wrong sizes, breached limits) are already contained by the harness, outside the agent's reach.
- Model economics — can a frontier boss plan and verify while cheaper workers execute?: A boss model would not catch what matters. Factual errors are caught by U9, where the script checks that each cited value actually matches the database at the cited table and date, not just that a citation exists. What is left is reasoning quality, and a critic can be persuaded by the same plausible thesis that persuaded the writer; the thesis structure (catalyst, key risk, falsifier, numeric exit level) lets the PM judge the argument in about 10 minutes. One strong model for S1 is better value than two.

Total > 0 → brigade. Total ≤ 0 → one cook. Low independence or low checkability can veto a positive score.

**Decision:** One cook, S1 · Research Analyst, because splitting off a thesis critic scores 0 after the coordination tax: it shares all context, isolates no permissions and adds a second plausible text rather than a cheaper check.

## A7 · The passing tray — decided on 2026-10-29

Work changes owner without making the human the corridor between tools.

- Ticket — ID · current owner · status · deadline · stop reason: One ticket per run (ID HF-YYYYMMDD-NN) with one row per idea keyed by idea_pipeline's idea_id (e.g. IDEA-009). Current owner: harness, S1 or PM. Run status: OPEN → AWAITING_GATE1 → IN_RESEARCH → AWAITING_GATE2 → CLOSED, or STOPPED; STOPPED is reserved for failures and always requires a stop reason; zero candidates is a valid outcome and ends CLOSED with the note '0 candidates – exceptions reviewed by PM' once the PM has reviewed the Exceptions at gate 1. Idea status: CANDIDATE, EXCEPTION, SELECTED, REJECTED, MEMO_READY, APPROVED, RESIZE, STOPPED. Deadline: the memo must reach the PM before the next market open; otherwise the data is stale and U1 re-pulls.
- Artifact — name · format · location · required structure (one role's output is literally the next role's input): All in my_kitchen/runs/<run-id>/. Harness → S1 (U2 → U3): candidates.json, up to 5 rows {idea_id, ticker, direction, rank, score, expected_return, horizon, pipeline_conviction, pipeline_thesis, source_table, snapshot_id}. S1 → harness (U3): reasons.json {idea_id, reason}, from which the harness builds shortlist.md. Harness → S1 (U4 → U5): selected.json, same fields, selected ideas only. S1 → harness (U6 → U7): conviction_<idea_id>.json {idea_id, conviction_proposed: integer 1–5} and nothing else; U7 takes expected return, horizon and book data from U1's extract, and volatility and liquidity never come from S1. S1's memo fields 2–6 go separately as memo_draft_<idea_id>.md, with fixed headings, to U9. The harness fills memo fields 1 and 8 directly from U1's extract, so the only numbers S1 writes are the data points cited in field 4 and the exit level in field 6. Harness → PM: shortlist.md (Exceptions on top) and memo.md (11 fields, field 11 blank). PM → harness: the PM's decision recorded in the ticket, per idea — SELECT/REJECT at gate 1, or APPROVE/REJECT/RESIZE at gate 2 — plus final conviction, target size if resizing, initials and timestamp; the PM updates the database status themselves.
- Evidence — sources · checks · assumptions · uncertainty · rejected alternatives: evidence.md, per tray: snapshot ID, source table and owner for every data field in the memo (if nobody owns a number, nobody can defend it in front of the PM); checks run and their results; assumptions (e.g. how horizon is read); every WITHHELD or MISSING input and why; rejected alternatives, i.e. the scores of all Pending ideas, including those below the top 5; and the limit-policy version. S1's own uncertainty goes in the memo's key-risk and falsifier fields.
- Acceptance + receipt — what the next station checks before accepting; who accepted or rejected, when, why, next state: The harness accepts through a named validation script that checks all fields are present, types are correct, conviction is an integer from 1 to 5 and not above the analyst's pipeline conviction, the score in memo field 7 matches conviction_<idea_id>.json, idea_id is on the selected list, and every citation's value matches the database. S1 does not re-check its input: the harness's pre-copy validation (row count, schema, snapshot ID, before anything is copied into s1/in/) is the acceptance step for harness → S1 trays, recorded as a receipt row, so the model never polices what code can check. Every pass adds a row to the ticket's handoff-receipts table: tray, from, to, timestamp, accepted by (script name and version, or PM initials), PASS/FAIL with the reason, and next state.
- Stop + rejection path — the condition that sends the packet back for repair: Back to S1 for repair: a schema failure or a citation mismatch, two attempts at most, after which the idea is STOPPED. Back to U1: a snapshot older than the last market close, or a tray whose snapshot ID does not match the ticket. Not a repair: missing volatility, liquidity or sector stays WITHHELD or FAIL, as designed. Stop the whole run (STOPPED): the database is unreachable, or the limit policy file is missing or unreadable (no limit check means no memo).

**Decision:** Every tray is a named file in the run folder with a fixed schema, accepted by a validation script or the PM's initials and logged as a receipt, so the human is never the corridor between tools and S1's only path into sizing is one integer.
